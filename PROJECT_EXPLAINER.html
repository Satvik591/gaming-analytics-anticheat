🎯 What Does This Project Do?

Imagine you're running an online multiplayer game like CS:GO or PUBG with thousands of players playing simultaneously. Two big problems arise:


  • 🚨 Cheaters — players using aimbot, speedhack, wallhack to ruin the game
  • 📊 Analytics — you need live leaderboards, match stats, player profiles

Our project is a data pipeline — a system that:

  • ✅ Collects millions of in-game events every second
  • ✅ Detects cheaters in real-time (under 200 milliseconds!)
  • ✅ Computes accurate leaderboards every hour
  • ✅ Shows everything on a live dashboard
💡 Think of it like this

A data pipeline is like a water pipeline. Water (data) flows from a source (game events), through pipes (Kafka), gets treated/filtered (Flink/Spark), stored in a tank (PostgreSQL/Redis), and finally comes out of your tap (Dashboard). Each part has a specific job.

🧠 Real World Analogies
Every technical concept explained using something you already know
1

🎮 Game Events → Like a CCTV Camera

Every action a player takes (moving, shooting, buying items, chatting) is recorded as an event. Just like a CCTV camera records everything happening in a mall — our game server records everything a player does, 15+ times every second.

2

📨 Kafka → Like a Post Office

All those events need to go somewhere immediately. Apache Kafka is like a post office — it receives all messages, sorts them into different boxes (topics), and holds them safely for 7 days. Anyone who needs a message can come and collect it from Kafka.

3

⚡ Apache Flink → Like a Security Guard (Real-time)

Flink watches every single event as it arrives — like a security guard watching the CCTV live. The moment it sees suspicious behaviour (too many headshots, moving too fast), it raises an alert immediately. It never waits.

4

🔵 Apache Spark → Like a Detective (Batch)

Spark is like a detective who reviews all recorded footage from the past hour and writes a detailed report. It's not watching live — it's processing all events together to compute accurate leaderboards and player stats. Runs every hour.

5

💾 Redis → Like a Whiteboard

Redis is an in-memory database — like a whiteboard. It's super fast to read and write, but it's not permanent (can be erased). We use it to store the latest fraud scores and live leaderboards so the dashboard can read them in under 1 millisecond.

6

🐘 PostgreSQL → Like a Filing Cabinet

PostgreSQL is a permanent database — like a filing cabinet. Everything is stored safely and can be queried anytime. Unlike Redis, data here survives restarts. This is where all historical transaction records live.

7

📊 Superset + Grafana → Like a TV News Channel

Superset shows business analytics (leaderboards, fraud reports, player profiles) — like the news anchor presenting the story. Grafana shows real-time system health and alerts — like the breaking news ticker at the bottom of the screen.

8

🛠️ dbt → Like a Chef's Recipe Book

dbt (data build tool) takes raw messy data from PostgreSQL and transforms it into clean, organized tables using SQL — like a chef taking raw ingredients and turning them into a proper dish following a recipe. It runs transformation "models" in order.

9

🐳 Docker → Like a Lunchbox

Docker packages each service (Kafka, Flink, etc.) into a container — like a separate compartment in a lunchbox. Each compartment holds exactly what it needs, doesn't mix with others, and the whole lunchbox (docker-compose) starts all of them together with one command.

Follow ONE event through the system
1

🎮 Player shoots someone → Event Created

Player "player_00042" gets a kill in match "match_a3f9". The game server (simulated by our Python producer) creates this JSON event and sends it to Kafka:

{ "event_id": "uuid-1234",
"player_id": "player_00042",
"match_id": "match_a3f9",
"event_type": "kill",
"is_headshot": true,
"reaction_time_ms": 62, ← ⚠️ suspiciously fast!
"accuracy_pct": 94.5, ← ⚠️ suspiciously high!
"timestamp": "2026-10-25T10:00:00Z" }
2

📨 Kafka receives and stores the event

Kafka puts this event in the player-events topic. It's now safely stored for 7 days. Kafka guarantees it won't lose this message even if a server crashes. Both Flink AND Spark can read it independently from Kafka.

3A

⚡ Flink reads it IMMEDIATELY (Speed Path)

Within milliseconds, Flink reads the event and runs it through cheat detection rules:
❌ reaction_time_ms = 62 → below 100ms threshold → AIMBOT SUSPECTED
❌ accuracy_pct = 94.5 → above 85% threshold → MACRO SUSPECTED
Flink then writes a fraud alert to the fraud-alerts Kafka topic and saves score to Redis.

3B

🔵 Spark reads it in the NEXT HOURLY BATCH (Batch Path)

One hour later, Spark reads ALL events from the past hour together. It recomputes the leaderboard from scratch, counting all kills, deaths, win rates for every player. This gives a 100% accurate result. It writes to PostgreSQL serving tables.

4

💾 Serving Layer: Redis + PostgreSQL

Redis now has: player_00042's fraud score = 0.87 (high risk!), live kill count = 18
PostgreSQL has: full transaction history, leaderboard table, cheat reports table
dbt runs SQL models to join and clean this data into beautiful final tables for dashboards.

5

📊 Dashboard shows the result

Grafana shows a red alert: "🚨 player_00042 flagged for AIMBOT — confidence 87%"
Superset shows in the cheat report dashboard: player profile, stats, which rules triggered, all flagged matches.
Total time from kill event → fraud alert on screen: < 200 milliseconds!

Architecture = the blueprint of how data flows and which tools handle what job. Just like a building's architecture decides where rooms, doors, and pipes go — data architecture decides how data moves through our system.

Lambda vs Kappa

⚖️ Lambda Architecture (Our Choice)

  • Has BOTH batch layer AND speed layer
  • Speed layer: fast but slightly approximate
  • Batch layer: slow but perfectly accurate
  • Combined serving layer gives best of both
  • More complex to build (better for projects!)
  • Perfect for leaderboards (need accuracy) + fraud (need speed)

🌊 Kappa Architecture (Alternative)

  • Only ONE path — the stream path
  • Simpler code — one processing engine
  • Replay = re-run the stream from Kafka log
  • Less accurate for historical aggregations
  • Easier to build (teacher said too simple!)
  • Good for pure real-time use cases
💡 Lambda analogy

Imagine a cricket match. The speed layer is the commentator giving you live ball-by-ball updates (fast, but sometimes makes mistakes). The batch layer is the statistician who reviews all footage after the match and publishes the official stats (slow, but 100% accurate). The serving layer combines both — you see live updates during the match, but official stats after.

🔑 Why Our Project Uses Lambda

  • 🏆 Leaderboards MUST be accurate — players will complain if rankings are wrong. Batch layer recomputes from ALL historical data.
  • 🚨 Fraud detection MUST be fast — we need to flag cheaters mid-match, not after. Speed layer catches them in <200ms.
  • 📚 More components = more learning — Lambda teaches Kafka, Flink, Spark, dbt, Redis, PostgreSQL all together.

Deep dive
🕵️ How Anti-Cheat Detection Works
The most interesting part of the project — explained simply

🎯 Two Detection Methods

We use two complementary approaches to catch cheaters. Together they catch almost everything:

⚡ Method 1: Rule-Based (Flink)

  • Runs in real-time on every event
  • Simple if/else rules
  • Catches known cheat types instantly
  • Result in <200ms
  • Can't catch unknown/new cheats

🤖 Method 2: ML Model (Spark)

  • Runs daily as batch job
  • Isolation Forest algorithm
  • Catches unusual patterns (even unknown)
  • Result after daily training run
  • Misses real-time incidents
Rule-Based Detection Rules
Cheat TypeWhat We MeasureThresholdWhy Suspicious?
🎯 Aimbot Headshot rate > 85% in 1-min window Pro human players average ~25-40%. 85%+ is physically impossible.
🎯 Aimbot Reaction time < 100ms consistently Human reaction time minimum is ~120ms. Under 100ms = computer-assisted.
💨 Speedhack Movement velocity > 300 units/sec Game engine has a hard speed limit of 300. Exceeding it = cheating software.
🖱️ Macro Accuracy consistency > 85% over 5+ events Humans have variance in accuracy. Too-perfect = automated clicking script.
👁️ Wallhack ML anomaly score Isolation Forest score < -0.1 Player always knows enemy positions perfectly — detected by ML as anomalous.
💡 Isolation Forest explained simply

Imagine you have 1000 player profiles. Most players cluster together (similar kill rates, similar headshot %, similar reaction times). Cheaters are isolated — their stats are far from the cluster. Isolation Forest finds these isolated outliers by trying to separate each player from the rest. Players that are easy to isolate (far from the group) get flagged as anomalies = likely cheaters.

Infrastructure deep dive
🐳 Docker — The Secret Glue of Our Project
What Docker is, why we need it, and exactly how it runs all 8 services in our project

🤔 What is Docker? (In One Line)

Docker is a tool that lets you package an application + everything it needs to run into a single portable box called a Container — so it runs the same way on every computer.

💡 Real World Analogy — Tiffin Box

Imagine you make a perfect meal at home. You want to send it to a friend. But if you just send the recipe, they might not have the same ingredients, same utensils, same oven.

Docker is like packing the entire meal + utensils + mini-oven into a tiffin box. Your friend just opens the box and the food is ready — exactly the same as what you made. No setup needed, no "it works on my machine" problems.

😩 The Problem Without Docker

Our project uses 8 different services. Without Docker, to run this project you'd have to:


ServiceWithout Docker — What You'd Need To Do
KafkaInstall Java, download Kafka, configure zookeeper.properties, start scripts manually
PostgreSQLInstall PostgreSQL 15 exactly, create users, set passwords, init database
RedisDownload Redis, compile from source (on some OS), configure max memory
FlinkInstall Java 11 exactly, download Flink 1.18, configure taskmanager slots
SupersetInstall Python, pip install 50+ packages, create admin user, run migrations
GrafanaDownload binary, configure ini file, install plugins manually

That's days of setup and it will break differently on every computer. 😭

✅ The Solution With Docker

With Docker, the entire setup is:

docker-compose up -d

That's it. One command. All 8 services start in 30 seconds. Same on your laptop, your friend's laptop, or a cloud server. 🎉

💡 Container vs Virtual Machine Analogy

Virtual Machine (VM) = Like renting an entire flat. You get your own kitchen, bathroom, bedroom — everything. Heavy, slow to start, uses lots of RAM.

Key Docker Concepts
1

🖼️ Docker Image — The Recipe

A Docker Image is a read-only template/blueprint. It contains the app + all its dependencies, but it's not running yet.

Analogy: An image is like a recipe card. The recipe describes every ingredient and step — but it's not food yet. You can make many meals (containers) from one recipe (image).

In our project: confluentinc/cp-kafka:7.5.0 is the official Kafka image. It already has Java + Kafka pre-installed inside it.

# Pull an image from Docker Hub (like downloading the recipe) docker pull confluentinc/cp-kafka:7.5.0
2

📦 Docker Container — The Running Instance

A Container is a running instance of an image. It's isolated from other containers (its own filesystem, network, process space) but shares the host OS kernel.

Analogy: Container = actual food cooked from the recipe. You can cook the same recipe (image) 10 times and get 10 separate meals (containers), each independent.

In our project: When Docker starts, it creates 8 separate running containers from 8 different images.

# Run a container from an image docker run --name kafka confluentinc/cp-kafka:7.5.0
3

🌐 Docker Network — The Private LAN

By default, containers can't talk to each other. Docker Networks create a private local network so containers can communicate using their names as hostnames.

Analogy: Like putting all 8 computers in the same office WiFi network. Once they're on gaming-net, Flink can reach Kafka by just typing kafka:9092 — no IP addresses needed.

In our project: All 8 services join gaming-net. That's why Flink's config says bootstrap.servers: kafka:9092 — "kafka" is literally the container name!

networks: gaming-net: # Our private network driver: bridge # Standard network type
4

💾 Docker Volume — Persistent Storage

By default, when a container stops, ALL its data is lost (like RAM). Docker Volumes mount a folder from your computer into the container so data survives restarts.

Analogy: Like plugging a USB drive into the container. Even if the container is destroyed and recreated, the USB drive (volume) keeps all the data safe.

In our project: PostgreSQL uses postgres_data volume — so all your game data is safe even if you restart the container.

volumes: postgres_data: # Named volume — survives container restarts redis_data: kafka_data:
5

🚢 Docker Compose — The Conductor

Docker Compose is a tool that reads a docker-compose.yml file and starts/stops multiple containers together in the right order with the right settings.

Analogy: Like a concert conductor. Instead of telling each musician (container) what to do one by one, the conductor (Compose) reads the score (yml file) and coordinates everyone to start at the right time, in the right order.

In our project: Compose starts Zookeeper first → waits for it → starts Kafka → waits → creates topics → then starts Flink, Postgres, Redis, Superset, Grafana.

docker-compose up -d # Start all services in background docker-compose ps # Check status of all services docker-compose logs -f # Watch live logs from all services docker-compose down # Stop and remove all containers
6

🏥 Health Checks — Auto-Recovery

Docker can automatically check if a container is actually working (not just running). If it's unhealthy, Docker can restart it or wait before starting dependent services.

In our project: Kafka's health check pings the broker API every 15 seconds. Only after Kafka is healthy does the kafka-init container start creating topics. This prevents startup race conditions.

healthcheck: test: ["CMD", "kafka-broker-api-versions", "--bootstrap-server", "localhost:9092"] interval: 15s # Check every 15 seconds timeout: 10s # Fail if no response in 10s retries: 10 # Try 10 times before marking unhealthy

🚪 What Are Ports? (And Why They Matter)

💡 Port Analogy

Think of your computer as a big apartment building. Each apartment has a number (port). Docker containers live inside the building. Port mapping creates a doorbell at the main entrance that rings a specific apartment inside.

29092:9092 means: "If someone knocks on door 29092 from outside → forward them to apartment 9092 inside the container."

🎯 Docker's Role in Each Phase of Our Project

PhaseWhat Docker Does
Phase 1 Runs Kafka (receives all 5 event streams) + PostgreSQL (stores raw events) + Redis (speed store) + Flink (speed layer anti-cheat job) — all from docker-compose up -d
Phase 2 Schema Registry container enforces Avro data contracts. Superset + Grafana containers serve the dashboards connected to PostgreSQL.
Phase 3 The full stack on EC2 — same docker-compose.yml runs identically on the cloud server as it does on your laptop. That's the beauty of containerization.

📋 Docker Commands Cheat Sheet

# ── Start / Stop ────────────────────────────────────────── docker-compose up -d # Start all containers in background docker-compose down # Stop and remove all containers docker-compose restart kafka # Restart only the Kafka container # ── Monitor ─────────────────────────────────────────────── docker-compose ps # See all containers + their status docker-compose logs -f # Watch live logs from ALL containers docker-compose logs kafka # See logs for only Kafka # ── Debug ───────────────────────────────────────────────── docker exec -it kafka bash # Go INSIDE the Kafka container docker stats # Live CPU + RAM usage per container # ── Cleanup ─────────────────────────────────────────────── docker-compose down -v # Stop + delete volumes (CAREFUL: loses DB data!) docker system prune # Clean up unused images/containers
🎓 Key takeaway: Docker turns a complex 8-service setup that would normally take days to configure into a single command that runs identically everywhere. That's why every modern data engineering project uses it.

🎯 One Paragraph Summary

We built a Lambda Architecture data pipeline for a gaming platform. Five Python producers simulate 15+ in-game events per second (player kills, match logs, chat, purchases, game state telemetry) and publish them to Apache Kafka. From Kafka, data flows into two parallel paths: the Speed Layer (Apache Flink) processes events in real-time to detect cheaters in under 200ms using rule-based detection and ML scoring, writing results to Redis; the Batch Layer (Apache Spark) runs hourly jobs to recompute accurate leaderboards and train an Isolation Forest ML model, storing results in PostgreSQL. dbt transforms raw PostgreSQL data into clean dashboard tables through staging → intermediate → mart layers. Finally, Apache Superset displays business analytics and Grafana shows real-time fraud alerts. The entire stack runs on Docker Compose with one command.
